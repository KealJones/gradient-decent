Gradient Decent / filter

Can a photo filter read handwriting?

An SVG filter, the thing meant for blurs and drop shadows, as a calculator. A handwritten-digit reader whose whole forward pass is one <filter>: the layers are feConvolveMatrix, the max pooling is feMorphology, and the activation function is the clamp every colour gets for free. No WebGPU, no WebGL, no WASM.

Yes. On the 10,000 MNIST test digits the filter gets 98.22% right and a plain JavaScript run of the same weights gets 98.24%. They give the same answer on 9,996 of them. The small gap is rounding: every picture inside a filter is 8 bits per channel, so every number in the network is rounded to one of 256 levels on the way through, and the network was trained expecting that. It's also slow: about 7 ms a digit, where a plain JavaScript loop is about 40 times faster in headless Chrome on a CPU. The race below measures your machine on 1,000 of those digits.

How one digit gets read

Seven steps. JavaScript does the first and the last, and none of the arithmetic. The five in the middle are filter primitives holding weights.

  1. JS
    Shrink the drawing.

    The pad is 280 pixels wide and the network takes 14×14. Your strokes are kept as lines and drawn again small: scaled so the digit's longer side is 10 pixels, centred, with a line about 1.2 pixels thick. That's how MNIST digits sit in their frame. The small picture gets a 1-pixel black border, making a 16×16 tile, and is drawn onto a canvas through the filter.

  2. Filter
    Copy.

    feTile repeats the tile 8 times in a 4×2 grid, one copy per kernel. The black borders keep the copies 2 pixels apart, which is exactly the zero padding a 5×5 kernel needs.

  3. Filter
    Convolve.

    Eight feConvolveMatrix primitives, each limited to its own copy, each with its own 5×5 kernel and bias. A filter's result is a colour, so anything below 0 becomes 0 and anything above 1 becomes 1. That clamp is the activation function, and it costs nothing.

  4. Filter
    Max.

    feMorphology with dilate is meant for thickening text. What it does is replace each pixel with the largest value in the 3×3 around it, which is max pooling. One primitive does all 8 maps at once.

  5. Filter
    Hidden layer.

    48 units, 6 per map. A unit that looks at a whole 14×14 map is a 14×14 kernel that only needs working out at one pixel, so each is a feConvolveMatrix whose output area is 1×1. An feOffset then moves that pixel into a row with the other 47.

  6. Filter
    Scores.

    Ten more feConvolveMatrix, each a 48×1 kernel laid over the row of hidden units and worked out at one pixel. The result is ten grey pixels, one per digit.

  7. JS
    Read back.

    One getImageData on those ten pixels. The brightest one is the answer. There's no softmax: the network was trained to make the right pixel white and the rest black.

  • Moving numbers to where the next layer reads them (feTile, feOffset, feMerge)

What it says

  • A filter is a small convolutional network already. Convolution, bias, a clamp and a max are all there as primitives. Nothing here is a trick on the scale of the CSS page; the primitives are used for what they do, just not for what they're for.
  • Everything is 8 bits, and that's fine if the network knows. Every primitive's result is rounded to one of 256 levels and clamped to 0..1. Training with the same rounding and clamping in place means the filter is the network, not an approximation of it: 98.22% against 98.24% without the rounding, on 10,000 test digits, and no score moved by more than 0.02.
  • The filter matches its own arithmetic exactly. A JavaScript version that rounds each layer to 8 bits gives the same answer as the filter on all 10,000 test digits, and no score differs by more than one step of 1/255. So the filter isn't roughly a neural network. It is this one.
  • It isn't fast. About 6 ms a digit in headless Chrome on a CPU, against about 0.16 ms for a plain JavaScript loop over the same weights. Merging the 48 feOffset primitives into 8 made no difference to the time.
  • The model is small and so is its idea of a digit. weights, trained on MNIST shrunk to 14×14. Apart from MNIST it has only been tried on strokes drawn by a script, not on many people's handwriting, so expect it to be wrong sometimes.

Gotchas found on the way

  • Pictures between primitives are 8 bits per channel, even when the canvas being drawn to is float16. Multiply by 0.01 in one primitive and by 100 in the next and 255 levels come back as 4.
  • Except when they aren't. Two feColorMatrix in a row are merged into one step and keep full precision between them, so the first precision test said everything was fine. Put any other primitive between them and it's 8 bits again.
  • feConvolveMatrix stops at 256 kernel entries. A 17×16 kernel doesn't raise an error. The primitive is skipped and the picture passes through untouched. So no single kernel can see all 8 feature maps, which is why the hidden layer has 6 units per map and not 48 units that each see everything.
  • Kernels of 28 entries or more are stored as an 8-bit picture, stretched between the kernel's smallest and largest entry. Up to 27 they're exact. The big kernels here were trained on that 256-level grid, which makes the filter exact again.
  • The kernel is applied upside down and back to front, as the specification says (it's a true convolution). Every kernel in the filter is written in reverse.
  • A primitive only writes where its input was. An feOffset that moves one pixel somewhere else produced nothing at all until it was given its own x, y, width and height, because its output area defaults to its input's.
  • A kernel can only write inside itself. targetX has to be smaller than the kernel's width, so a hidden unit's pixel lands on the map it's looking at and needs an feOffset to get anywhere useful.
  • bias is added everywhere, including the empty space between tiles, so every convolution is fenced in with x, y, width and height.
  • Filters work in linear light by default. Without color-interpolation-filters="sRGB" every number is bent through a gamma curve on the way in and back out: half of 200 came out as 147.
  • Only tried in headless Chrome 153 with no GPU, where filters run in software. The canvas asks for software drawing (willReadFrequently) to keep it that way, but a different browser, or a GPU path with different rounding, could give different numbers. The race above will show it if so.
