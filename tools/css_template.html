Gradient Decent / css

Can a stylesheet run a language model?

A tiny character-level model, trained on lowercase Shakespeare, whose whole forward pass is CSS colour maths. Every activation is an rgb(), every weight block is a relative-colour transform, every sum is a color-mix().

Yes, and it gets the maths right: it matches a plain JavaScript run of the same weights to about 0.005, and picks the same top character every time. It's just very slow. The browser's style engine is hundreds of times slower than a plain JavaScript loop (85 to 770 times in the scaling test below; the race measures your machine), and every weight costs about 21 bytes of stylesheet. The babble is the 21,000-weight model's fault, not the CSS's.

How one character gets made

Seven steps per character. JavaScript does three of them and none of the arithmetic.

  1. JS
    Tokenise.

    Take the last 8 characters, look up each one's number in the 37-character vocabulary, and write them as class names on one div: s0t1 s1t20 … s7t14 means "token 1 at position 0" and so on.

  2. CSS
    Embed.

    Each of the class rules sets the colours for one token at one position. The 8 positions × 9 numbers come out as 24 colours, --x0 to --x23.

  3. CSS
    Layer 1: 72 inputs to 192 neurons.

    The weight matrix is cut into 3×3 blocks. Each block is a relative colour: take input colour i, and make a new colour whose red is r*a + g*b + b*c, and so on. That's a 3×3 matrix times a 3-vector, which is all a colour matrix is.

  4. CSS
    Sum.

    The blocks for one output colour are added with a binary tree of color-mix(). Mixing averages, so the weights are pre-multiplied by the number of leaves (32 here) and the average comes out as the sum. The bias is one more leaf.

  5. CSS
    ReLU, then layer 2.

    calc(max(r, 0)) on each channel. The result lands in a registered @property --h0 { syntax: '<color>' }, which the next layer reads with var(), the same way, to make 13 logit colours.

  6. JS
    Read back.

    One getComputedStyle and 13 getPropertyValue calls. Reading forces Chrome to resolve every expression in one style recalc. That's the whole forward pass.

  7. JS
    Sample.

    Softmax with temperature and pick one character. Then go back to step 1 with it on the end.

What it says

  • Chrome keeps colour channels as unclamped floats. color(srgb -4.8 7.12 52.5) survives a round trip, so a colour is a three-number register. Only alpha is clamped to 0 to 1, which makes rgba really rgb: three lanes, not four.
  • CSS costs about 1.6 µs per weight per character, flat. From 21K to 670K weights it stays linear. Nothing broke: a 14 MB stylesheet loaded in under 2 seconds. A one-million-weight model would be about 1.6 seconds per token.
  • A JavaScript loop is 85 to 770 times faster in this test. The live race above can land higher, since a warm loop over a 21K model barely touches memory. The gap closes as the model grows because the JS loop starts missing the CPU cache, not because CSS gets better.
  • Every weight is about 21 bytes of text. A float, a multiply sign and a share of the surrounding calc(). Ternary weights would shrink each term to + r, - g or nothing.
  • Precision is fine. Values come back with about 6 significant digits, and the logits match the JavaScript run to about 0.005.

Gotchas found on the way

  • tanh() isn't a CSS maths function. Using it makes the whole declaration invalid, and the colour silently falls back to black. exp(), pow(), sqrt(), max() and clamp() work.
  • color-mix() premultiplies by alpha, so alpha has to stay at 1 or it scales the numbers.
  • The vocabulary has 37 characters, which isn't a whole number of colours. The first version only had room for 36 logits, so it could never write &. Now it pads to 39 with logits that can't win.
  • Only tried in Chrome. Safari has relative colour syntax, but nobody has checked whether it keeps out-of-range channels.
