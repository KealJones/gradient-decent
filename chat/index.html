Gradient Decent / chat

Can a 2D canvas hold a conversation?

A 1.8-million-weight chat model, TinyChat-1776K, where every matrix multiply is done by blending colours on a 2D canvas. The weights are pictures, the multiply is a blend mode, the sum is an image being squashed and the activation function is a gradient. No WebGPU, no WebGL, no WASM.

Yes, and it gets the maths right: on a 136-token test conversation it picks the same next token as the original model in Hugging Face transformers at every position. The odd answers are the model's fault, not the canvas's. It was trained on conversations at a three-year-old's level and knows nothing about the world. A plain JavaScript loop is still much faster; the race below measures by how much on your machine.

Run it

Ask it about cats, cake or its favourite colour. Don't ask it for facts. It keeps the whole conversation in mind for about 250 tokens.

How one token gets made

22 matrix multiplies per token, every one of them on the canvas. JavaScript does the bookkeeping around them.

  1. JS
    Tokenise.

    Your message is wrapped as <A>your text <end> followed by <B>, the model's turn, and cut into pieces with byte-pair encoding from a 2,048-piece vocabulary.

  2. JS
    Embed and normalise.

    Look up the token's row of numbers, then scale it so its average size is 1 (RMSNorm). This is the input vector for the layer.

  3. Canvas
    Multiply.

    The input becomes a 2-pixel-tall strip of colours. It's stretched over the weight picture with the multiply blend mode, so every pixel becomes one weight times one input.

  4. Canvas
    Sum.

    The product is drawn at half its width, again and again, with smoothing on. Each halving averages neighbouring pixels, so when a row is one pixel wide that pixel is the row's average, which is the sum divided by the width.

  5. JS
    Read back.

    One getImageData on a 1-pixel-wide column returns every output of the multiply at once. Red plus green from the top half, minus the same from the bottom half, times a scale.

  6. JS
    Attention.

    Three of those multiplies give a query, a key and a value. The key and value are cached. The query is compared with every cached key, the scores go through a softmax, and the values are mixed in those proportions. This is how it remembers earlier tokens.

  7. Canvas
    The gradient.

    The feed-forward part needs SiLU, a smooth curve. It's stored as a canvas linear gradient with 1,025 colour stops, rendered once. Applying it is reading the colour at the right position, like an eyedropper.

  8. JS
    Repeat, then sample.

    3 layers of seven multiplies each, then one more against the vocabulary picture to score every possible next token. Pick one, show it, and go back to step 1.

What one multiply looks like

strip.putImageData(input, 0, 0)                  // the vector, as a 2-pixel-tall strip
work.globalCompositeOperation = 'copy'
work.drawImage(weights, 0, 0)                    // the matrix, as a picture
work.globalCompositeOperation = 'multiply'
work.drawImage(strip, 0, 0, w, 2, 0, 0, w, h)    // every weight times its input, in one draw
for (half of halvings) half.drawImage(prev, 0, 0, pw, h, 0, 0, pw / 2, h)   // sum by squashing
answer = last.getImageData(0, 0, 1, h)           // one pixel per output

That's the real sequence from lib/blend.js, trimmed. Negative numbers can't be colours, so positives go in the red channel and negatives in green, and the strip is drawn twice (once swapped) so all four sign combinations get multiplied.

The weights themselves

All 22 of them. One pixel is one weight: red is positive, green is negative, brighter is bigger. Every picture in a row is drawn at the same scale. Click one to see it up close.

What it says

  • Blend modes are exact enough. In a float16 canvas a multiply lands within about 0.2% of the true answer, and the logits end up within 0.17 of the real model's on values around 20. In an ordinary 8-bit canvas the same multiply is about 5% off, which is too much.
  • Full-precision weights fit in 8-bit pictures. Each pixel holds 8 bits of size, the channel holds the sign, and every row has its own scale. Against the original weights that moves the logits by about 0.06 and changes none of the top tokens.
  • It runs at about 15 tokens a second in headless Chrome on a CPU with no GPU, with the tiles drawing.
  • It isn't fast. A plain JavaScript loop over the same weights is about 19 times faster per token in headless Chrome on a CPU. The race above gives the number for your machine. The canvas is here because you can watch it.

Gotchas found on the way

  • Squashing a picture to one pixel in a single drawImage gives garbage, because the browser only samples a few pixels. Halving step by step is what makes it a sum.
  • Colours can't be negative, so every number is split into a positive and a negative channel and the multiply is done for all four sign combinations.
  • This model's vocabulary has glued-together pieces (a full stop, an end marker and the next speaker's tag as one token) that its own tokenizer never produces. They're blocked at sampling.
  • Only tried in Chrome. It needs a float16 2D canvas.
